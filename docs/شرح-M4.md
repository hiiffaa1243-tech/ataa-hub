# شرح المرحلة M4 — حوكمة الصرف

هذه المرحلة تضمن أن **المال المقيّد لا يُصرف إلا على مشروعه، ولا يتجاوز رصيده أبداً**، وأن كل صرف يمر بسلسلة موافقات مسجّلة ثم يظهر قيداً في الدفتر.

---

## الرصيد المتاح

```
الرصيد   = إيرادات المشروع − مصروفاته (من دفتر الأستاذ)
الملتزم به = طلبات صرف «معتمدة» لم تُصرف بعد
المتاح   = الرصيد − الملتزم به
```

الطلب المعتمد "يحجز" مبلغه حتى قبل صرفه، فلا يستطيع طلب آخر أن يأخذ نفس المال.

**قفل السطر:** قبل كل فحص رصيد يُقفل سطر المشروع في قاعدة البيانات (`SELECT … FOR UPDATE`). لو ضغط شخصان "اعتماد" في نفس اللحظة على نفس المشروع، ينتظر الثاني حتى ينتهي الأول، ثم يُفحص الرصيد من جديد. فلا يُصرف نفس الريال مرتين.

---

## طلب الصرف (Disbursement Request)

```
مسودة ─(مدير المشروع: إرسال للمراجعة)→ بانتظار مراجعة المحاسب
      ─(المحاسب: اعتماد)→ بانتظار اعتماد المدير التنفيذي      (أو: إرجاع → مسودة)
      ─(المدير التنفيذي: اعتماد)→ معتمد                       (أو: رفض، والسبب إلزامي)
      ─(المحاسب: تأكيد الصرف)→ مصروف  ← قيد يومية
```

- **فحص الرصيد عند كل خطوة للأمام**: الإرسال، واعتماد المحاسب، واعتماد المدير، والصرف. في الإرسال تُحفظ لقطة "المتاح وقت الطلب".
- **عند الصرف** يُنشأ قيد: **مدين** حساب المصروف / **دائن** حساب البنك، والمشروع على السطرين. ينزل رصيد المشروع، وتبقى نسبة الإنجاز كما هي لأنها تُحسب من التبرعات فقط.
- **إلغاء قيد الصرف** (مثلاً صُرف من البنك الخطأ) يُرجع الطلب إلى "معتمد" ويمسح رابط القيد، فيمكن صرفه من جديد صحيحاً.
- لا يُلغى طلب مصروف قبل إلغاء قيده.
- كل خطوة تخص دوراً واحداً: مدير المشروع لا يعتمد طلبه، والمحاسب لا يعتمد مكان المدير التنفيذي.
- **التنبيهات**: الشخص التالي في السلسلة يصله تنبيه داخل النظام (الجرس).

## التخصيص من الصندوق العام (Fund Allocation)

الطريق **الوحيد** لنقل مال غير مقيّد (تبرعات الصندوق العام) إلى مشروع مقيّد:

```
مسودة ─(مدير المشروع أو المحاسب: طلب)→ بانتظار اعتماد المدير التنفيذي
      ─(اعتماد)→ معتمد ← قيد   |   ─(رفض، بسبب)→ مرفوض
```

- **القيد**: مدين "تحويلات صادرة" (المشروع العام) / دائن "تحويلات واردة" (المشروع المقيّد). ينقص رصيد العام ويزيد رصيد المشروع بنفس المبلغ، ولا تتأثر "إيرادات التبرعات" ولا نسبة الإنجاز.
- **فحص الرصيد** عند الطلب وعند الاعتماد: لا يتجاوز المتاح في الصندوق العام.
- يسمح فقط بالتحويل من صندوق غير مقيّد إلى مشروع مقيّد.
- **الإلغاء** من المستند نفسه يعكس القيد. أما إلغاء قيد التخصيص مباشرة من شاشة القيود فممنوع.

## الملفات وشرح كل واحد

| الملف | وظيفته |
|---|---|
| `doctype/disbursement_request/*.json/.py/.js` | جدول طلب الصرف ومنطقه وشاشته. الشاشة تعرض الرصيد والملتزم به والمتاح، وتفلتر حسابات المصروف والبنك |
| `doctype/fund_allocation/*` | جدول التخصيص ومنطقه وشاشته |
| `ataa_hub/spending.py` | أدوات مشتركة: هل تغيّرت الحالة، رسالة "رصيد غير كافٍ"، من يحمل دوراً معيناً، التنبيهات، وإنشاء القيد المرتبط بالمستند وإلغاؤه |
| `ataa_hub/accounting.py` | أُضيف `lock_project` (قفل السطر)، و`get_available` (المتاح مع استثناء الطلب نفسه)، ودالة تعرض الرصيد للشاشة بعد التحقق من الصلاحية |
| `ataa_hub/setup/workflows.py` | ينشئ مساري الموافقة (الحالات، والانتقالات، ومن يملك كل خطوة) عند التثبيت وكل تحديث، فتطابق قاعدة البيانات الكود دائماً. وينشئ **ملفات الأدوار** |
| `ataa_hub/overrides/journal_entry.py` | `on_cancel` جديد: إلغاء قيد صرف يُرجع الطلب لـ"معتمد". قيود التبرع والتخصيص لا تُلغى إلا من مستندها |
| `ataa_hub/permissions.py` | مدير المشروع يرى طلبات الصرف والتخصيصات الخاصة بمشاريعه فقط. والمشروع للقراءة فقط لغير مدير المشروع |

## ملفات الأدوار (Role Profiles)

أدوارنا تعطي صلاحيات عطاء، وأدوار ERPNext الأصلية تعطي الوصول لجداوله (المشروع، القيد، العميل). ملف الدور يجمعها في اختيار واحد عند إنشاء المستخدم:

| الملف | الأدوار |
|---|---|
| Ataa Accountant | محاسب التبرعات + Accounts User + Projects User + Sales User |
| Ataa Project Manager | مدير المشروع + Projects User |
| Ataa Executive Director | المدير التنفيذي + Projects User + Auditor |

## ملاحظة تقنية مهمة: Frappe v16

في v16، إذا رجعت دالة الصلاحية `has_permission` بـ`None` يعتبرها Frappe **رفضاً**. في v15 كانت تُتجاهل. أصلحنا الدوال لترجع `True` (أي: لا اعتراض، وصلاحيات الدور تقرر)، وأضفنا اختباراً يمنع رجوع المشكلة.
